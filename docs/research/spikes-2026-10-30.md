# Phase 0 spikes (2026-10-30)

These spikes were run on Basel's Mac (macOS, arm64) to settle the open questions in SYNTHESIS §8 before P1. The throwaway code lived in the session scratchpad and is not in the repo. What follows is the evidence and what it changes.

## 1. Claude Code `mcp_tool` hooks, session ids, tool visibility

**Setup:**
- Claude Code **2.1.312** (the VS Code extension's bundled binary; the `claude` on PATH is 2.1.97).
- `claude -p … --plugin-dir <spike> --setting-sources project --output-format stream-json`, run from a project directory whose path contains a space.
- The spike plugin had:
  - a dependency-free stdio MCP server that speaks only the 2025 era and logs every message and its env;
  - `mcp_tool` hooks for SessionStart, UserPromptSubmit, PreToolUse (`WebSearch|WebFetch|Bash`) and Stop;
  - a shell-form sh/PowerShell polyglot preflight (`. "${CLAUDE_PLUGIN_ROOT}/hooks/preflight.ps1"`);
  - an app-only probe tool.
- There were two runs: (1) a plain question, and (2) "run `echo spike`, then use the built-in WebSearch tool".

| Question | Result |
|---|---|
| Does `${session_id}` substitute in `mcp_tool` `input`? | **Yes**, for UserPromptSubmit, PreToolUse and Stop |
| Do `${tool_name}`, `${tool_input.query}`, `${tool_input.command}` substitute? | **Yes.** Missing paths become `""`. `${agent_type}` is `""` for the main agent |
| Does the server get `CLAUDE_CODE_SESSION_ID` / `CLAUDE_PROJECT_DIR` / `CLAUDECODE`? | **Yes.** The session id equals the hook `session_id`. `CLAUDE_PROJECT_DIR` was correct with a space in the path. Keys from the plugin's `.mcp.json` `env` arrived |
| `CLAUDE_PLUGIN_DATA` for a `--plugin-dir` plugin | `~/.claude/plugins/data/shspike-inline` |
| Does UserPromptSubmit fire before any tool call? | **Yes** (≈ 2.5 s before the first model tool call) |
| Do SessionStart `mcp_tool` hooks run at startup? | **No:** "mcp_tool hooks are not available for the 'SessionStart' hook event (no MCP client context)", as documented. UserPromptSubmit covers re-keying |
| Does the shell-form polyglot preflight run (macOS)? | **Yes**, via `sh`. Its `systemMessage` was delivered. Windows and Git Bash remain untested |
| Does a PreToolUse deny steer the model to our tool? | **Yes.** WebSearch was denied with our reason, and the model immediately called our `search` with the same query |
| Is the Stop `systemMessage` shown once, without continuation? | **Yes**: "Stop says: SPIKE receipt: 1 search(es) this session" (level `notice`) |
| **Does Claude Code hide `_meta.ui.visibility: ["app"]` tools from the model?** | **Yes.** The app-only probe was absent from the session's tool list |
| **Can an `mcp_tool` hook call an app-only (model-hidden) tool?** | **Yes.** With `hook` marked app-only, it vanished from the model's tool list, and every hook call still reached it |
| Does `_meta["anthropic/alwaysLoad"]` skip tool-search deferral? | **Yes.** `search` was in the initial tool list, while WebSearch itself needed ToolSearch |
| Protocol negotiation | Claude Code sent `server/discover` **in-process on the same stdio connection** (id `server-discover-probe-1`, `_meta` protocolVersion `2026-07-28`, clientInfo `claude-code` 2.1.312, capabilities `roots`, `elicitation.form/url`). On `-32601` it fell back to `initialize` with `2025-11-25` on the same process. **No sibling probe process** |
| Extra `_meta` on `tools/call` | `claudecode/toolUseId` (the transcript's `tool_use` id) and `progressToken` |

**Consequences:**
- `hook` becomes app-only and model-invisible in Claude Code (ADR-0012, ADR-0014). Turn bracketing stays as defence in depth.
- `apply_rule` can also be registered for Claude Code, where it is hidden and usable by the Desktop Code tab's panel.
- `claudecode/toolUseId` is stored on search rows for transcript correlation.

## 6. Filtering Claude Code's built-in WebSearch with hooks (no engine)

**Question.** Can search-hole govern Claude Code's own `WebSearch` instead of replacing it?

**Setup.** Same harness as §1 (Claude Code 2.1.312), with node command hooks on `PreToolUse(WebSearch)` and `PostToolUse(WebSearch|WebFetch)`.

| Test | Result |
|---|---|
| PreToolUse `updatedInput` adds `blocked_domains: ["wikipedia.org"]` | **Applied.** PostToolUse saw `tool_input.blocked_domains: ["wikipedia.org"]`, so Anthropic's search filtered server-side |
| WebSearch `tool_response` shape | `{ query, results: [ { tool_use_id, content: [ { title, url } … ] }, "<summary text written by the search step>" ], durationSeconds, searchCount }`. **Titles and URLs only: no snippets, no dates** |
| PostToolUse `updatedToolOutput` drops `debugbear.com` and `logrocket.com` entries | **Applied.** The model's tool result contained neither domain, and its URL list omitted both (2 hidden). `additionalContext` was delivered alongside |

**Caveats:**
- The summary string is written by the search step from the results it saw. Domains passed in `blocked_domains` are excluded upstream, so the summary is clean for them. Results removed only in PostToolUse (regex or path rules) may still be mentioned in the summary, so the summary needs rewriting or a warning note.
- The cap on the number of `blocked_domains` entries is unknown and needs testing.
- This works only in Claude Code (and possibly Cursor and Codex, whose hooks are untested). Claude Desktop, claude.ai, ChatGPT, VS Code and Zed offer no such hook.

→ [ADR-0018](../adr/0018-claude-code-builtin-search-mode.md)

## 7. Result quality: Claude's built-in WebSearch vs local SearXNG (5 queries, same hour)

**Method.** I ran the same five queries through (a) Claude Code 2.1.312 built-in WebSearch, with `tool_response` captured by a PostToolUse hook, and (b) local SearXNG with our overlay (upstreams: Google CSE, DuckDuckGo, Brave, Wikipedia). "Official" means the project's own docs or repo domain.

| Query | Built-in: results · official in top 5 · snippets · dates | SearXNG: results · official in top 5 · snippets · dates |
|---|---|---|
| react compiler | 9 · **1** · none · none (top: a third-party docs site, logrocket, a translation mirror `az.react.dev`) | 40 · **4** · 40/40 · 16/40 (react.dev ×4; noise: online-compiler sites) |
| python asyncio taskgroup | 9 · **0** · none · none (slingacademy, aiotools, PyPI, Android/Debian source mirrors) | 37 · **1** · 37/37 · 10/37 (**docs.python.org #1**, then geeksforgeeks, reddit, SO) |
| node sqlite DatabaseSync | 6 · 2 · none · none (nodejs.org RC docs, then **scraped `node_modules` copies on unrelated domains**) | 26 · 2 · 26/26 · 0/26 (bun.com reference, **nodejs.org/api #2**, deno docs) |
| best budget mechanical keyboard 2026 | 9 · — · none · none (Tom's Hardware ×3, a mirrored blog, **`*.pages.dev` SEO farms ×2**) | 27 · — · 27/27 · 0/27 (rtings, Tom's Hardware, reddit, Wirecutter; some vendor blogs) |
| kubernetes pod crashloopbackoff fix | 9 · 0 · none · none (vendor marketing blogs) | 20 · 0 · 20/20 · 0/20 (vendor blogs, Stack Overflow) |

**What it shows:**
1. **The built-in search is noisier for developer queries.** It returns mirrors, scraped copies and SEO farms, and sometimes omits the official docs entirely. That is exactly what search-hole's rules and lists target, so filtering it is valuable even alone. But "prefer official docs" can't work when the official page isn't in the result set at all, and there are no snippets or dates for freshness.
2. **SearXNG gives better raw material** (official docs present and usually first, snippets, some dates) and allows the full pipeline: ranking, freshness, engine fusion.
3. **SearXNG degrades under agent volume.** After about 15 queries that hour, its Brave upstream reported `too many requests`, then `Suspended`, and DuckDuckGo returned `CAPTCHA` (all visible in `unresponsive_engines`). A keyed engine alongside it, or the filtered built-in search as a fallback, keeps results flowing.

**Decision taken:** the `auto` mode in [ADR-0018](../adr/0018-claude-code-builtin-search-mode.md).

**Addendum (same day): every hook can be an `mcp_tool` hook.** In an `mcp_tool` PostToolUse hook, `"${tool_response}"` and `"${tool_input}"` substitute as **JSON strings** (parse them in the gateway). The `updatedToolOutput` returned in the tool's text was applied: the stripped results never reached the model. So built-in filtering runs in-process in the gateway, and no Node command hook is needed.
